## Descrição

Implementar autenticação JWT (JSON Web Tokens) no backend Express, permitindo que usuários façam login com email/senha e recebam um token JWT para acessar APIs protegidas.

Resultado: Endpoints `/auth/login` e `/auth/refresh` funcionais, middleware de validação JWT, testes de autenticação.

---

## Acceptance Criteria

### Login Endpoint
- [ ] `POST /auth/login` aceita email + senha (JSON)
- [ ] Valida credenciais contra tabela `users` (bcrypt)
- [ ] Retorna `{ accessToken, refreshToken, user: { id, email, nome, role } }` em sucesso
- [ ] Retorna erro 401 se credenciais inválidas
- [ ] Retorna erro 400 se email/senha faltando

### Token Generation
- [ ] Access token válido por 15 minutos
- [ ] Refresh token válido por 7 dias
- [ ] Tokens assinados com chave secreta (JWT_SECRET env var)
- [ ] Tokens contêm claims: `userId`, `email`, `role`, `iat`, `exp`

### JWT Middleware
- [ ] Middleware `authMiddleware` valida token em requests
- [ ] Extrai `userId`, `email`, `role` do token e coloca em `req.user`
- [ ] Retorna erro 401 se token inválido/expirado
- [ ] Retorna erro 403 se token não fornecido

### Refresh Token Endpoint
- [ ] `POST /auth/refresh` aceita `{ refreshToken }`
- [ ] Valida refresh token
- [ ] Retorna novo access token + refresh token
- [ ] Retorna erro 401 se refresh token inválido/expirado

### Protected Routes
- [ ] `GET /api/health` permanece público (sem JWT)
- [ ] `GET /api/empresas` requer JWT válido
- [ ] Request autenticado contém `req.user` com dados do usuário

### Testing
- [ ] Teste de login com credenciais válidas
- [ ] Teste de login com credenciais inválidas
- [ ] Teste de token expirado
- [ ] Teste de refresh token
- [ ] Teste de middleware rejeitando requisições sem token

### Documentation
- [ ] Documentação de autenticação (docs/AUTHENTICATION.md)
- [ ] Instruções de .env (JWT_SECRET, TOKEN_EXPIRY)
- [ ] Exemplos de uso de endpoints

## Dev Notes

### JWT Payload Structure
```typescript
interface JWTPayload {
  userId: number;
  email: string;
  role: 'admin' | 'contador' | 'gerente' | 'visualizador';
  iat: number;
  exp: number;
}
```

### Token Expiry Strategy
- **Access Token:** 15 minutos (expiração rápida, segurança)
- **Refresh Token:** 7 dias (permite renovação sem re-login)
- Frontend deve chamar `/auth/refresh` quando access token expirar

### Security Considerations
- JWT_SECRET deve ter mínimo 32 caracteres (use `openssl rand -base64 32`)
- Tokens nunca devem incluir senha ou dados sensíveis
- HTTPS obrigatório em produção
- Token no header `Authorization: Bearer <token>` (não em cookie por enquanto)

### Database Integration
- AuthService faz query na tabela `users` criada em STORY-1.2
- Usa `bcrypt.compare()` para validar senha_hash
- Retorna informações públicas do usuário (id, email, nome, role)

### Key Decisions

1. **Access Token Expiry:** 15 minutos (segurança) vs 24h (conveniência) → 15m venceu por segurança
2. **Refresh Token Expiry:** 7 dias (standard web) vs 30 dias → 7 dias venceu
3. **Token Storage:** Header `Authorization: Bearer` (vs localStorage) → Header é mais seguro
4. **Middleware Pattern:** Separate `authMiddleware` + `optionalAuthMiddleware` → Flexibilidade para rotas públicas/protegidas
